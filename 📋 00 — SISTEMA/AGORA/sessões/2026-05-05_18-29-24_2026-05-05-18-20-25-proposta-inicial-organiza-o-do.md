# Proposta Inicial: Organização do Obsidian para Otimização

## Diagnóstico do problema
"Otimização" é ambíguo. Vou assumir 3 objetivos práticos que costumam ser o real problema de quem busca isso:
1. **Encontrar** notas rapidamente (recuperação).
2. **Conectar** ideias sem virar bagunça (atrito baixo na captura).
3. **Performance** do app (vault grande não travar).

Se o objetivo for outro, ajusto na próxima rodada.

---

## Estrutura proposta: PARA-Zettel híbrido

Abandone hierarquias profundas. Use **5 pastas-raiz fixas** + tags + links.

```
/00_Inbox          ← captura crua, processada semanalmente
/10_Notes          ← notas atômicas permanentes (zettel)
/20_Projects       ← coisas com prazo e entregável
/30_Areas          ← responsabilidades contínuas (saúde, trabalho, finanças)
/40_Resources      ← referências, livros, artigos, clips
/99_Archive        ← projetos concluídos / áreas inativas
/_meta             ← templates, attachments, scripts
```

**Regra de ouro:** profundidade máxima de 2 níveis. Se precisar de mais, use tags ou links.

## Convenções (executáveis amanhã)

### Nomenclatura
- Notas atômicas: `título-descritivo-curto.md` (kebab-case, sem data no nome).
- Daily notes: `YYYY-MM-DD.md` em `/_meta/daily/`.
- Reuniões: `YYYY-MM-DD - assunto.md` em `/20_Projects/<projeto>/`.

### Frontmatter padrão (todas as notas permanentes)
```yaml
---
created: 2026-05-05
tags: [tipo/conceito, dominio/programacao]
status: seedling   # seedling | budding | evergreen
source: 
---
```

### Tags em 2 eixos apenas
- `tipo/...` (conceito, pessoa, ferramenta, livro, projeto)
- `dominio/...` (programacao, financas, saude, etc.)

Isso evita explosão de tags. Tudo que não for um desses dois eixos vira **link**, não tag.

## MOCs (Maps of Content) em vez de pastas profundas

Para cada **Area** e cada **domínio importante**, crie uma nota MOC:
- `MOC - Programação.md`
- `MOC - Finanças.md`

Use Dataview para popular automaticamente:
```dataview
LIST FROM #dominio/programacao
SORT file.mtime DESC
```

Isso resolve "onde guardo isso?" — guarde em `/10_Notes` e o MOC encontra.

- Criar as 6 pastas-raiz.

**Dia 2 — Configuração (1h)**

**Dia 4 — Criar 3 MOCs principais** (30 min)

**Dia 5 — Rotina de revisão**
- Agendar revisão semanal de 20 min: esvaziar `/00_Inbox`, promover notas seedling → evergreen.

## Métrica de sucesso (em 30 dias)
- Tempo médio para encontrar uma nota < 15s.
- `/00_Inbox` zerado pelo menos 1x por semana.
- Pelo menos 50% das notas novas têm 1+ link de saída.

### Análise Crítica da Proposta:

1.  **PROBLEMA: Rigidez Excessiva do Sistema de Tags (Eixo Único de Semântica)**
    *   **POR QUE IMPORTA:** A limitação estrita a apenas dois eixos de tags (`tipo/` e `dominio/`) é o ponto mais vulnerável da proposta. Embora a intenção seja evitar a "explosão de tags", ela ignora o fato de que tags são ferramentas poderosas para categorização multifacetada, filtragem rápida e estabelecimento de múltiplos contextos. Muitos usuários se beneficiam de tags para indicar:
        *   **Status/Progresso:** (e.g., `#ideia`, `#rascunho`, `#publicado`, `#pendente`)
        *   **Ação/Prioridade:** (e.g., `#follow-up`, `#importante`, `#bug`)
        *   **Pessoas/Equipes:** (e.g., `#joao`, `#equipe-marketing`)
        *   **Emoção/Relevância:** (e.g., `#insight`, `#pergunta`)
        *   **Formatos:** (e.g., `#checklist`, `#grafico`)
        Forçar todos esses conceitos para links (que exigem uma nota existente) ou para a categoria `tipo/` ou `dominio/` pode ser artificial, gerar atrito desnecessário e levar o usuário a abandonar a convenção ou a criar tags "proibidas", bagunçando o sistema.
    *   **SUGESTÃO:** Flexibilizar o sistema de tags, mantendo os eixos `tipo/` e `dominio/` como *primários* e *altamente recomendados*, mas permitindo uma camada adicional de tags "livres" ou um terceiro eixo mais genérico (e.g., `meta/` ou `status/`).
        *   **Alternativa 1 (Mais Flexível):** Manter `tipo/` e `dominio/` como os eixos *principais* para MOCs e organização de conteúdo, mas permitir que outras tags sejam usadas livremente para categorização ad-hoc, com a recomendação de mantê-las concisas e limitadas em número para evitar sobrecarga.
        *   **Alternativa 2 (Estruturada):** Adicionar um terceiro eixo `status/` ou `acao/` para tags de fluxo de trabalho.
        *   Em ambos os casos, enfatizar que tags *sempre* devem ser usadas para **categorização** ou **metadados**, enquanto links são para **conexão semântica**.

2.  **PROBLEMA: Processo de Migração de Vaults Legados Grandes é Insuficiente**
    *   **POR QUE IMPORTA:** O Executor reconhece a incerteza aqui, e com razão. Para usuários com milhares de notas em um vault legado, simplesmente "mover o resto para `/99_Archive/_legacy/` em bloco" é uma simplificação perigosa. Pode resultar em:
        *   **Perda de Contexto:** Notas importantes (ou que *pareciam* importantes) ficam "enterradas" no arquivo, sem um processo claro para resgatá-las.
        *   **Links Quebrados:** Se a estrutura de pastas e nomes de arquivo for radicalmente diferente, muitos links internos podem quebrar, invalidando as conexões existentes.
        *   **Sobrecarga Cognitiva:** O usuário pode se sentir paralisado pela vasta quantidade de conteúdo não processado, levando à frustração e abandono.
    *   **SUGESTÃO:** Detalhar o processo de migração para vaults legados, dividindo-o em fases e adicionando salvaguardas:
        *   **Backup Obrigatório:** A primeira etapa, antes de tudo, deve ser um backup completo do vault existente.
        *   **Ferramentas de Análise:** Sugerir o uso de ferramentas para identificar notas com muitos links de entrada (`Links to this note`) ou notas "órfãs" antes de arquivar. O próprio Dataview pode ajudar a listar notas com poucos ou nenhum link.
        *   **Estratégia de Resgate Gradual:** Em vez de apenas arquivar, propor um plano de "resgate" gradual do arquivo. Por exemplo, dedicar 15-30 minutos semanais para "pescar" 5-10 notas relevantes de `/99_Archive/_legacy/`, integrá-las à nova estrutura (renomear, adicionar frontmatter, links), ou descartá-las se realmente não forem úteis.
        *   **Considerar Novo Vault:** Para vaults *extremamente* grandes e desorganizados, sugerir a criação de um vault totalmente novo com a estrutura proposta, mantendo o antigo como um "arquivo de referência" somente leitura. Isso permite um novo começo limpo sem perder o histórico.
        *   **Tratamento de Links Quebrados:** Mencionar plugins como "Link Kicker" ou "Broken Links" e estratégias para lidar com eles durante a migração.

3.  **PROBLEMA: Profundidade Máxima de 2 Níveis Pode Criar Fricção para Projetos Complexos**
    *   **POR QUE IMPORTA:** A regra de ouro de "profundidade máxima de 2 níveis" é excelente para atomicidade, mas pode ser um ponto de atrito para projetos que, por sua natureza, possuem sub-projetos, fases ou módulos bem definidos que se beneficiam de uma organização visual e hierárquica mais profunda para anotações específicas. Por exemplo, em `/20_Projects/ProjetoX/`, um usuário pode querer subpastas para `/Reuniões/`, `/Pesquisas/` ou `/Subprojeto A/`. A ausência de uma pasta clara para essas subdivisões pode levar a uma "explosão de notas" no nível 2, dificultando a navegação visual em vez de simplificá-la, ou a uma sobrecarga de tags/

## Mudança 1: Sistema de tags em 3 eixos + zona livre controlada

**Eixos canônicos (obrigatórios para notas permanentes):**
- `tipo/...` — natureza da nota (conceito, pessoa, livro, ferramenta, reuniao)
- `dominio/...` — área de conhecimento (programacao, financas, saude)
- `status/...` — fluxo de trabalho (rascunho, ativo, pendente, evergreen, arquivado)

**Zona livre (opcional, ad-hoc):**
- Tags simples sem prefixo, para fluxo pontual: `#follow-up`, `#insight`, `#bug`, `#pergunta`.
- **Regra de governança:** auditoria mensal via Dataview. Se uma tag livre apareceu em 5+ notas e persistiu por 2 meses, ela "graduou" — converta em link (se for entidade) ou em prefixo formal (se for metadado).

**Princípio que separa tag de link:**
- **Tag** = atributo da nota (estado, categoria, formato). Resposta a "como esta nota é?".
- **Link** = relação com outra entidade. Resposta a "com o que esta nota se conecta?".
- Pessoas, projetos, livros e conceitos são **entidades** → viram nota + link, nunca tag.

Query para auditar tags livres:
```dataview
TABLE length(rows) AS "Uso"
FROM ""
FLATTEN file.tags AS t
WHERE !contains(t, "/")
GROUP BY t
SORT length(rows) DESC
```

## Mudança 3: Protocolo de migração de vault legado (substitui o Dia 3 anterior)

### Pré-requisito: triagem do tamanho
- < 500 notas: migração direta (plano original).
- 500–3000 notas: protocolo abaixo.
- \> 3000 notas ou caos extremo: **vault novo** + legado como referência somente-leitura.

### Fase 0 — Salvaguardas (obrigatório, 30 min)
1. **Backup completo** (zip + sync externo: Git, Drive, etc.).
2. Snapshot do estado atual: total de notas, tags existentes, plugins ativos.
3. Instalar plugins de apoio: **Janitor** (notas órfãs), **Link Kicker** ou **Find Orphaned Files** (links quebrados).

### Fase 1 — Análise (1h)
Antes de mover qualquer coisa, classificar notas por sinais objetivos via Dataview:

```dataview
TABLE 
  length(file.inlinks) AS "Entradas",
  length(file.outlinks) AS "Saídas",
  date(today) - file.mtime AS "Idade"
FROM ""
SORT length(file.inlinks) DESC
```

Categorias:
- **Núcleo vivo**: editada nos últimos 90 dias OU 3+ inlinks → migra para nova estrutura.
- **Dormente útil**: inlinks > 0 mas inativa → vai para `/99_Archive/_legacy/` mas entra na fila de resgate.
- **Órfã antiga**: 0 inlinks, 0 outlinks, > 1 ano → candidata a descarte (revisar em lote).

### Fase 2 — Migração do núcleo vivo (2h, time-boxed)
- Mover apenas notas do "núcleo vivo".
- Usar **Obsidian rename** (não mv do SO) para preservar links.
- Adicionar frontmatter padronizado em lote via script ou Templater.

### Fase 3 — Arquivo estruturado do legado
- `/99_Archive/_legacy/` **espelha a estrutura antiga** (não joga tudo em uma pasta só).
- Adicionar nota `_legacy/README.md` documentando: data da migração, critério usado, como buscar.

### Fase 4 — Resgate gradual contínuo
- Bloco semanal de 20 min: "pescaria de arquivo".
- Meta: 5 notas/semana → resgatar (com frontmatter novo) ou descartar definitivamente.
- Após 12 semanas, reavaliar: o que sobrou no `/_legacy` provavelmente não vale resgate.

### Fase 5 — Reparo de links quebrados
- Rodar plugin de detecção de links quebrados.
- Corrigir apenas links em notas do núcleo vivo. Links no legado ficam quebrados — é aceitável.

### Análise Crítica da Proposta (Rodada 2):

1.  **PROBLEMA: Governança da "Zona Livre" de Tags é Frágil e Dependente da Disciplina Humana**
    *   **POR QUE IMPORTA:** A ideia de uma "zona livre" de tags para uso ad-hoc é uma boa concessão à flexibilidade, mas sua governança ("auditoria mensal via Dataview") é um ponto de fragilidade. A proposta assume que o usuário terá a disciplina, o tempo e a clareza mental para realizar essa auditoria mensal de forma consistente e eficaz. Em cenários de baixa motivação, alta carga de trabalho ou simples esquecimento, essa governança pode falhar, levando à proliferação descontrolada de tags livres, revertendo o problema que o sistema tentou evitar. A "graduação" de tags livres para prefixos formais é uma ótima intenção, mas a execução depende de um processo manual que pode ser esquecido ou negligenciado.
    *   **SUGESTÃO:**
        *   **Automatizar o Alerta:** Em vez de apenas uma query para "auditoria", criar um alerta mais proativo. Por exemplo, um script Dataview/Templater que, ao ser executado, *lista* as tags que não atendem aos critérios de "graduação" (menos de X usos, menos de Y tempo) e as apresenta como um "to-do" na nota principal de revisão semanal.
        *   **Regras de "Degradação":** Definir explicitamente o que acontece se a auditoria falhar. Em vez de "graduar", o que acontece com tags que *não* se tornaram úteis ou formais? Elas devem ser removidas proativamente? Sugerir um script que, após a auditoria manual de aprovação, possa remover tags não aprovadas com um clique.
        *   **Estratégia de "Limpeza":** Tornar a "limpeza" de tags indesejadas parte da rotina de revisão semanal, não apenas uma auditoria mensal. Por exemplo, dedicar 5 minutos na revisão semanal para escanear rapidamente as tags recém-adicionadas e remover as claramente inadequadas ou redundantes.

2.  **PROBLEMA: A Distinção entre Tag, Link e Inline Field (Dataview) Não é Completamente Explorada ou Resolvida**
    *   **POR QUE IMPORTA:** A proposta de v2 menciona explicitamente em "Pontos onde ainda tenho incerteza" que "Em vaults com forte uso de dataview inline fields (ex: `prioridade:: alta`), a fronteira tag/link/field fica nebulosa". Esta é uma crítica material. A distinção entre Tag (atributo genérico), Link (conexão semântica) e Inline Field (atributo específico e estruturado, muitas vezes para consultas Dataview) é crucial para um sistema robusto. Ao não definir claramente como inline fields se encaixam na estrutura, o usuário pode criar inconsistências:
        *   Campos que poderiam ser tags (`prioridade:: alta` vs. `#prioridade/alta`)
        *   Campos que poderiam ser links (`responsavel:: [[João]]` vs. linkar a nota `João`)
        *   Duplicação de informações (usar ambos tag e campo para o mesmo conceito).
        Isso pode levar a consultas Dataview conflitantes ou ineficientes e a uma organização semântica confusa. A nota de incerteza é um reconhecimento, mas a proposta não oferece uma *direção* clara sobre como o usuário deve proceder quando encontra essa nebulosidade.
    *   **SUGESTÃO:**
        *   **Definição Clara de Inline Fields:** Estabelecer uma diretriz clara sobre o uso de inline fields:
            *   Usar inline fields para *dados estruturados* que serão frequentemente consultados e filtrados via Dataview (e.g., `data-vencimento:: YYYY-MM-DD`, `valor:: 100`, `completo:: true/false`).
            *   Se um inline field tem uma lista finita de valores que se assemelha a uma categoria (como `status:: ativo`), considerar convertê-lo em uma tag (`#status/ativo`) ou link para uma nota de status (se a complexidade justificar).
            *   Para referenciar entidades (pessoas, projetos), dar preferência a `[[links]]` em vez de inline fields (`responsavel:: [[João]]` é redundante se a nota já linka para João). Inline fields para referências só fariam sentido se fosse para um *atributo específico* da entidade referenciada, algo que um link sozinho não captura (ex: `projeto-principal:: [[ProjetoX]].duracao`).
        *   **Estratégia de Migração de Campos Legados:** Se o usuário tem muitos inline fields legados, orientar sobre como analisá-los (via Dataview para listar todos os campos únicos) e decidir se eles devem se tornar tags, links ou serem mantidos como campos estruturados na nova organização.

3.  **PROBLEMA: O Escalonamento da Profundidade em `/20_Projects` Pode Levar à Fragmentação Excessiva e Dificuldade de Visão Geral**
    *   **POR QUE IMPORTA:** Permitir "até 4 níveis" para projetos é uma melhoria necessária, mas a ausência de um "guardião" contra a fragmentação excessiva dentro dessa estrutura livre pode criar um novo tipo de problema. Um projeto muito complexo poderia acabar com dezenas de subpastas e notas aninhadas, tornando o `_index.md` do projeto uma MOC sobrecarregada ou difícil de navegar. A regra "se uma subpasta tem < 5 notas e nenhuma estrutura clara, ela não deveria existir" é um bom ponto de partida, mas pode ser insuficiente para projetos que têm muitas fases pequenas e distintas. O risco é que a estrutura do projeto se torne *tão* complexa quanto a hierarquia que se tentou evitar nas outras pastas.
    *   **SUGESTÃO:**
        *   **Ênfase na MOC do Projeto:** Reforçar o papel do `_index.md` (ou `_MOC.md`) dentro de cada pasta de projeto. Este arquivo deve ser o centro de navegação e visão geral do projeto. Ele pode conter:
            *   Links para todas as subpastas principais.
            *   Links diretos para as notas mais importantes do projeto (entregáveis chave, decisões críticas).
            *   Trechos de Dataview que listam notas por status ou tipo dentro do projeto.
        *   **Diretriz de Profundidade por Tipo de Projeto:** Em vez de um limite numérico de níveis, sugerir que a profundidade seja ditada pela *complexidade intrínseca* do projeto e pela necessidade de clareza. Projetos simples podem ter 1-2 níveis. Projetos muito complexos (e.g., desenvolvimento de software com múltiplos módulos, pesquisa acadêmica com diversas vertentes) podem justificar mais níveis.
        *   **Limitação Baseada em "Semântica Clara":** Encorajar a criação de subpastas apenas quando elas representam um *agrupamento semântico claro e estável*. Uma pasta `/relatorios/` é clara. Uma pasta `/notas-do-dia-15-maio-2027-sobre-ideia-nova/` não é. Isso evita a criação de pastas baseadas em tempo ou em eventos pontuais, que deveriam ser contidas nas notas ou no `_index.md`.

4.  **PROBLEMA: O "Vault Novo" como Solução para Caos Extremo pode ser Desencorajador e Ignorar o Valor de Notas "Dormentes Úteis"**
    *   **POR QUE IMPORTA:** Para vaults com > 3000 notas ou "caos extremo", a sugestão de um "vault novo + legado como referência somente-leitura" é pragmática, mas pode ser desalentadora. Isso implica um esforço significativo para reintroduzir dados e, mais importante, pode levar o usuário a subestimar ou a não aproveitar as notas "dormentes úteis" que foram arquivadas. A proposta de "resgate gradual contínuo" é ótima para o protocolo de migração, mas menos aplicável se o legado é um arquivo separado e de difícil acesso/manipulação. O risco é que o usuário "abandone" o legado completamente, perdendo informações valiosas que poderiam ser integradas gradualmente.
    *   **SUGESTÃO:**
        *   **Facilitar a Integração do Legado:** Se um vault novo é escolhido, oferecer estratégias para tornar a consulta ao legacy menos árdua. Isso pode incluir:
            *   Usar o Obsidian URI scheme para linkar entre o vault novo e o vault de legado.
            *   Se o legacy não for *tão* caótico, considerar importar *apenas* as notas marcadas como "dormente útil" para o novo vault, já devidamente processadas.
        *   **Redefinir "Caos Extremo":** Clarificar o que constitui "caos extremo". São muitas notas? Links quebrados? Formatação inconsistente? A solução de vault novo deve ser um último recurso, não uma primeira opção para qualquer vault grande.
        *   **"Cura" do Legacy como Alternativa:** Em vez de um vault novo, propor um processo de "cura" intensiva do vault existente. Isso pode envolver scripts mais agressivos, ajuda de IA para reestruturação ou um período focado de refatoração, em vez de um abandono total.

---

**Reconhecimento:** A inclusão de plugins como Janitor/Link Kicker especificamente para a fase de migração, e a sua posterior desinstalação recomendada, é uma abordagem madura para evitar a sobrecarga contínua de plugins. A adaptação da profundidade por pasta-raiz é uma correção vital.

Apesar destas críticas, a proposta está evoluindo muito bem e está muito mais robusta. A base para um sistema organizado e adaptável está cada vez mais sólida.

## A. Sistema semântico unificado: Tag, Link, Inline Field

Esta é a tabela de decisão que faltava. **Quando estiver em dúvida, consulte:**

| Você está representando... | Use | Exemplo |
|---|---|---|
| Atributo categórico finito (estado, tipo, domínio) | **Tag com prefixo** | `#status/ativo`, `#tipo/conceito` |
| Atributo categórico ad-hoc (temporário) | **Tag livre** | `#follow-up`, `#insight` |
| Conexão com uma entidade (pessoa, projeto, conceito, livro) | **Link** | `[[João Silva]]`, `[[ProjetoX]]` |
| Dado estruturado para consulta/filtragem (data, número, booleano) | **Inline field** | `vencimento:: 2026-06-01`, `valor:: 250` |
| Atributo *sobre* uma entidade já linkada | **Inline field + link** | `responsavel:: [[João]]` |

**Regras de exclusividade (evita duplicação):**
1. Se um inline field tem ≤ 5 valores possíveis → vire tag prefixada.
2. Se um inline field só aponta para entidades → vire link inline (`[[entidade]]` no corpo da nota).
3. Nunca use tag E inline field para o mesmo conceito na mesma nota.

**Migração de inline fields legados:**
```dataview
TABLE without id 
  meta(field).field AS "Campo",
  length(rows) AS "Uso"
FROM ""
FLATTEN file.frontmatter AS field
GROUP BY meta(field).field
```
Aplicar a tabela de decisão acima a cada campo encontrado.

## B. Governança de tags com automação leve

Substituo "auditoria mensal" por **3 camadas de defesa**, da mais leve à mais pesada:

### Camada 1 — Limpeza semanal (5 min, dentro da revisão semanal)
Query rodada na nota de revisão semanal:
```dataview
TABLE length(rows) AS "Uso"
FROM "" WHERE file.ctime >= date(today) - dur(7 days)
FLATTEN file.tags AS t
WHERE !contains(t, "/")
GROUP BY t
```
Lista tags livres adicionadas na última semana. Decisão imediata: manter, renomear ou remover.

### Camada 2 — Alerta mensal automatizado (Templater)
Template `revisao-mensal.md` gera automaticamente uma seção:
- **Tags candidatas a graduação** (≥5 usos, ≥2 meses): listar com ação sugerida.
- **Tags candidatas a remoção** (1 uso, >3 meses): listar para limpeza em lote.
- **Tags duplicadas semanticamente** (heurística: similaridade de nome): revisar manualmente.

### Camada 3 — Regra de degradação explícita
Se a auditoria mensal **não acontecer por 2 meses seguidos**, o sistema entra em "modo conservador":
- Bloquear adição de novas tags livres (apenas mental — o usuário se compromete).
- Próxima revisão obrigatoriamente faz limpeza retroativa.

Isso reconhece honestamente que disciplina humana falha, e cria um circuit breaker.

## C. Profundidade em `/20_Projects`: critério semântico

Substituo "até 4 níveis" pela **regra dos 3 testes**. Crie uma subpasta apenas se ela passar nos 3:

1. **Teste do agrupamento estável:** o conteúdo desta subpasta vai existir por toda a vida do projeto? (Reuniões: sim. "Notas-da-segunda": não.)
2. **Teste do nome semântico:** o nome da subpasta é uma categoria substantiva, não temporal nem episódica? (`/pesquisa/`: sim. `/discussao-julho/`: não.)
3. **Teste da massa crítica:** vai conter ≥ 5 notas no horizonte de 3 meses? (Se não, deixe plano e use links/tags.)

**Reforço do papel do `_index.md`:**

Toda pasta de projeto (qualquer nível) tem `_index.md` com estrutura mínima:
```markdown
# ProjetoX

inicio:: 2026-05-05

## Visão geral
[3 linhas sobre o projeto]

## Entregáveis-chave
- [[entregavel-1]]
- [[entregavel-2]]

LIST FROM "20_Projects/ProjetoX"

```

Isso garante que profundidade não vira labirinto: o `_index.md` é sempre a porta de entrada.

## D. "Caos extremo" definido + porta aberta entre vaults

### Definição operacional de caos extremo
É a situação em que **2+ destes critérios** estão presentes:
- > 3000 notas E > 30% sem nenhum link.
- > 20% das notas têm links quebrados.
- Mistura de 3+ sistemas organizacionais abandonados (pastas antigas, tags inconsistentes, MOCs órfãs).
- Frustração do usuário ao ponto de evitar abrir o vault.

Se apenas o tamanho é grande (> 3000 notas) mas há coerência → **não é caos extremo**, use o protocolo padrão de migração.

### Alternativa antes do "vault novo": Cura intensiva
Para vaults grandes mas não caóticos:
- **Sprint de refatoração:** 1 semana, 2h/dia, focado em normalização.
- **Triagem por amostragem:** processar 100 notas/dia aleatoriamente em vez de tentar cobrir tudo.
- **Aplicação de templates em lote** via Templater + script (adiciona frontmatter padrão).

### Quando o vault novo é a escolha: ponte com legado
Se mesmo assim o vault novo for necessário:
1. **Vault legado vira read-only** mas **não inacessível**: configure no Obsidian como segundo vault aberto.
2. **Use Obsidian URI** para linkar do novo para o velho: `obsidian://open?vault=Legacy&file=nota-x`
3. **Importação seletiva**: notas marcadas como "dormente útil" na Fase 1 são importadas pré-processadas (não jogadas no `/_legacy`, mas integradas direto na nova estrutura).
4. **Fila de resgate** continua viva, agora apontando para o vault legado em vez de pasta `/_legacy/`.
